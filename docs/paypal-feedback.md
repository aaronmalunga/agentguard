# PayPal developer friction log

Honest, evidence-backed notes from building AgentGuard on PayPal (sandbox). Written for PayPal's developer and product
teams, and for the "rate your PayPal experience" question on the hackathon form. Each entry says **how we know**:
*measured* (we ran it), *read in source* (we checked the SDK code), or *from docs* (PayPal's or the plugin's docs).

| # | Date | Area | What happened | Impact on an agent payment product | How we know | Suggestion |
|---|---|---|---|---|---|---|
| 1 | 14 Oct, re-run 5 Nov | Orders v2 | A **declined** card returns **HTTP 201** on create-order; the decline is only in `authorizations[0].status = DENIED`. | Code (or an AI agent) that checks only the HTTP code thinks the payment succeeded. We key every decision on payment status. | Measured (`spike/results/`, 17/17 reproduced 22 days apart) | Call this out at the top of the Orders error docs; consider a non-2xx or an explicit `payment_status` field for single-step card orders. |
| 2 | 14 Oct | Agent toolkit | `create_order` in PayPal's agent toolkit hard-codes `intent=CAPTURE`. | An agent can't hold a payment for a human to approve. We create AUTHORIZE orders in our own code instead. | Read in source (spike v2, decision D4) | Expose `intent` (AUTHORIZE) in the toolkit; human-in-the-loop is exactly what agent payments need. |
| 3 | 14 Oct | Payments v2 | Card authorisations last **29 days**; reauthorise only once, between day 4 and 29. Clear and well enforced (422 `REAUTHORIZATION_TOO_SOON`). | Sets the longest a payment can wait for a human; we auto-void before the honour period ends. | Measured | Positive. A one-line summary table of auth windows per funding source would help. |
| 4 | 14 Oct | Idempotency | `PayPal-Request-Id` worked every time: 0 duplicate charges in 3 replays (capture, refund, tracking). | This is what makes retries safe for agents. | Measured | Positive. |
| 5 | 14 Oct | Vault | Saved cards (Vault) are US-only in sandbox for our setup, so we use US sandbox accounts. | Developers outside the US test with US accounts and US fee examples. | ADR-0004 (account setup) | A clearer country/feature matrix on the Vault page. |
| 6 | 14 Oct, 5 Nov | Sandbox | Sandbox calls took **0.45–4.3 s** (median ~2–3 s). | Slow for a checkout-path guard; we keep PayPal calls out of our latency budget and report them separately. | Measured (METRICS.md) | Publish typical sandbox latency so teams don't mistake it for production. |
| 7 | 5 Nov | Server SDK (Python 2.4.0) | `Environment.PRODUCTION` is enum value **0**, and `Environment.from_value()` accepts ints and returns `None` for unknown values instead of raising. A stray `0` or a typo can select live or nothing, silently. (The 2.4.0 default is SANDBOX, which is good.) | For money-moving code, a silent fall-through to live is the worst failure. We pass SANDBOX explicitly and also check the resolved base URL host. | Read in source (`configuration.py`); flagged by the Context Plugin | Make `from_value` raise on unknown values; consider requiring `environment` explicitly. |
| 8 | 5 Nov | Server SDK | Passing `None` for an optional model field serialises an explicit `null`; the SDK expects `APIHelper.SKIP` to omit a field. Easy to get wrong. | Our first version sent `"attributes": null` on cards. Caught by our tests. (Not yet tested whether the live API rejects it.) | Measured against our fake; behaviour read in source | Treat `None` as "omit" for optional request fields, or document SKIP prominently. |
| 9 | 5 Nov | Server SDK | Network and proxy failures surface as raw `requests` exceptions, not `ApiException`; auth failures are `AuthValidationException`, also not an `ApiException`. | A caller catching only `ApiException` crashes on a timeout, and can't tell "PayPal down" from "bad keys". We map all three to one error type that says "outcome unknown, retry with the same request id". | Measured (our test); auth exception read in source (`apimatic_core`) | One SDK base exception for all failures, with a flag for "outcome unknown". |
| 10 | 5 Nov | APIMatic Context Plugin | The plugin's Python skills pointed us to the SDK traps in rows 7 and 9, to building the client once (token caching), and to stubbing the OAuth token endpoint separately in tests. | Five of our gateway's design rules came straight from the plugin (see `docs/decision-log.md`, 5 Nov). | Used while building | Positive. |

## Overall (draft for the form, update before 11 Nov)
Reliable and reproducible sandbox; idempotency is excellent. Biggest friction for **agent** payments: the 201-on-decline
surprise (#1) and the agent toolkit's CAPTURE-only orders (#2), because holding a payment for a human is the core safety
control for agents. SDK sharp edges (#7–#9) matter more when an AI writes or calls the code.
