find a hole?" Each finding says what we did about it. Status: **Fixed** (done today), **Planned** (day named), or

## B. Payments code
| # | Finding | Why it matters | Status |
|---|---|---|---|
| B1 | PayPal keeps **create-order** idempotency keys for only **6 hours** (SDK docstring; capture keys: 45 days). A retry after 6 h with the "same" key creates a **second** authorisation. | Double hold on the buyer's card; the budget reservation would also be wrong. | **Planned (Fri):** store every request id with its outcome; before any retry, read back the order by our `reference_id`; never retry a create after 6 h without that read-back. |
| B2 | `sandbox_test_card()` (a card number) lives in the product gateway module. | A payments-security reviewer (PCI scope) will flag product code that touches card numbers, even test ones. | **Planned (Fri):** move it to tests/scripts; document that production vaulting uses PayPal-hosted card fields or a PayPal-wallet vault setup, so AgentGuard never sees card data. |
| B3 | Capture doesn't check the captured amount against the authorised amount and the mandate. | Defence in depth on the one call that takes money. | **Planned (Fri).** |
| B4 | `money()` always uses 2 decimals; zero-decimal currencies (e.g. JPY) would be wrong. | Silent 100× errors outside USD. | **Planned (Fri):** currency allowlist (USD only in the sandbox) with a clear error. |
| B5 | The "order APPROVED → authorise" path (PayPal-wallet buyer approval) is untested; the fake doesn't model it. | Untested money path. | **Planned (Sat)** with the buyer approval flow. |
| B6 | No scheduler yet for the authorisation honour period / 29-day expiry (auto-void, spike decision D2). | Held payments could lapse instead of being voided at $0. | **Planned (Sat/Mon)**; this is also the only honest reason for a Bryntum timeline (N6). |
| B7 | `PENDING` captures are reported as "not succeeded" with no follow-up. | A capture can complete later. | **Planned (Sat):** webhooks (verified, deduplicated). |
| B8 | **The gateway hasn't run against the real sandbox yet** (Claude's shells can't reach PayPal). Everything so far ran against FakePayPal. | The fake copies proven behaviours, but SDK serialisation against the live API is unproven. | **Fixed (5 Nov, 15:18):** Aaron ran the live smoke test: **9/9 steps as expected** through the product code (`spike/results/2026-11-05_1518_gateway_smoke.json`). One fidelity gap found and fixed in the fake: a replayed capture returns HTTP 200, not 201. |
| B9 | FakePayPal could be mistaken for PayPal in a demo, the exact weakness we criticise in other entries. | Credibility. | **Rule:** the hosted judge demo uses the real sandbox; FakePayPal is only for local runs and CI, and the UI shows a "FAKE PAYPAL" banner when it's on. No latency figure is ever taken from it. |

## C. Governance and evidence
| # | Finding | Why it matters | Status |
|---|---|---|---|
| C1 | "Ask" currently means *authorise and hold*. For a page with a detected injection, holding money on the buyer's card for something they may not want is itself a harm. | Holds reach the issuer (ADR-0001). | **Open (D1).** Recommendation: two kinds of ask. *Ask-first* (nothing sent to PayPal) when the signal is manipulation; *hold* when the doubt is price or item, so one tap captures. |
| C2 | A mandate "signed" by our own server is weak dispute evidence: the merchant is vouching for itself. | The dispute-evidence claim (N1) is our most novel one; a payments judge will test it. | **Open (D2).** Recommendation: (a) the buyer approves the mandate in a PayPal-side step (wallet approval / vault setup), and (b) the receipt hash goes into the PayPal order's `custom_id`, so PayPal's own record carries a timestamped fingerprint of the intent. Needs a sandbox check that the field round-trips. |
| C3 | A hash-chained log in our own database can be rewritten end to end by whoever runs the database. | Tamper-*evident* only against outsiders. | **Planned (Sat):** anchor the chain head periodically in S3 Object Lock (ADR-0008) and/or PayPal `custom_id` (C2). |
| C4 | Nothing stops an agent from calling PayPal directly if it ever gets PayPal credentials. | The guard only works if it is the only path to money. | **By design:** the agent never holds PayPal credentials; only the guard does (operator = merchant). **Planned:** a test that the agent process has no PayPal secrets in its environment. |
